## 摘要

C/C++程序中的缓冲区越界等空间内存错误可能造成数据破坏、程序崩溃甚至控制流劫持。Arm Memory Tagging Extension（MTE）通过比较指针标签与内存标签检测非法访问，但传统方案通常随机分配标签。在MTE仅提供4位标签的情况下，相邻对象可能获得相同标签，攻击者也可能通过重复尝试或侧信道获取标签信息，因此随机标签主要提供概率性保护。

StickyTags将标签从一次性的随机属性改为与内存空间位置绑定的持久属性。该方法按对象尺寸类别组织堆和栈区域，使连续对象槽采用确定性的16标签轮转，从而在标签周期限定的范围内为跨对象访问提供确定性保护。同时，持久标签避免在每次分配和释放时反复标记内存，有利于降低运行开销。

本实验基于论文作者公开的StickyTags修改版LLVM/SafeStack和TCMalloc，在Windows 11、WSL2和QEMU AArch64 MTE环境中完成机制级初步复现。实验自行设计了堆栈越界功能测试、标签轮转测试、边界距离测试、标签持久性测试、MTE粒度测试和保护版/未保护版对照测试。结果显示：20轮功能对照中，未保护版堆、栈越界均未产生MTE故障，保护版堆、栈越界均以100%的比例产生MTE专用故障；保护版860条机制测试全部通过，680个预期MTE故障全部被观察到，未出现普通段错误被误计为MTE故障的情况；10000次持久性迭代中发生9990次地址复用，未观察到标签变化。上述结果支持StickyTags确定性标签轮转、有限距离空间保护、标签持久性以及堆栈覆盖等核心设计。本实验未复现真实Arm设备性能、SPEC、Juliet、真实CVE和侧信道实验，因此结果只支持功能与机制层面的初步复现结论。

## 1. 实验背景

### 1.1 空间内存错误

C和C++允许程序直接操作指针和内存，这种灵活性也带来了空间内存安全问题。当程序使用一个对象的指针访问对象边界之外的地址时，就会产生空间越界。常见形式包括栈缓冲区溢出、堆缓冲区溢出、越界读、越界写以及由类型混淆引起的跨对象访问。

越界访问的影响取决于目标位置和访问方式。越界读可能泄露敏感数据，越界写可能破坏相邻对象、函数指针或控制数据。传统边界检查能够提供较完整的保护，但通常需要在大量内存访问前插入检查，可能带来较高的运行开销。因而，如何在保护能力和运行开销之间取得平衡，是内存安全研究的重要问题。

### 1.2 Arm MTE基本原理

Arm MTE为指针和内存分配标签。指针高位保存逻辑标签，内存以16字节为粒度保存分配标签。程序执行内存访问时，处理器比较两者：

```text
指针逻辑标签 == 内存分配标签：允许访问
指针逻辑标签 != 内存分配标签：产生MTE标签检查故障
```

在64位AArch64系统中，MTE逻辑标签通常位于指针高字节中的4位，因此最多有16个标签值。MTE可以通过同步或异步模式报告故障。本实验采用异步模式，Linux将标签检查错误报告为`SEGV_MTEAERR`；测试程序也兼容同步模式的`SEGV_MTESERR`。

### 1.3 传统随机标签方案的不足

传统MTE方案通常在对象分配时随机选择标签，并在对象释放时重新标记内存。随机标签使攻击者难以直接预测目标对象标签，但其保护具有以下限制：

1. MTE只有4位标签，标签空间较小；
2. 相邻对象可能随机获得相同标签；
3. 当源对象和目标对象标签相同时，跨对象访问不会触发标签检查故障；
4. 攻击者可能通过重复尝试、暴力猜测或推测执行侧信道寻找匹配标签；
5. 反复进行内存标记可能造成额外运行开销。

因此，随机标签的空间错误检测通常只能给出概率保证，而不能保证附近对象一定使用不同标签。

### 1.4 StickyTags的研究目标

StickyTags关注有界空间内存错误。它不依赖标签保密，而是把标签设计为空间布局的一部分：即使攻击者知道全部标签，也无法使用当前对象的带标签指针访问标签周期内的其他对象槽。该方法的目标是在较低开销下形成较大的确定性空间保护范围，并通过持久标签减少重复内存标记。

## 2. StickyTags核心设计

### 2.1 按尺寸类别组织内存

StickyTags按size class组织对象。一个区域中的槽位保存相同尺寸类别的对象，因此连续对象槽之间的距离是固定的。假设对象尺寸类别为`S`，连续槽位的地址间隔也是`S`。固定间距使实现可以根据区域基址、对象地址和尺寸类别计算标签，而不需要为每个对象单独保存随机标签元数据。

堆对象由修改版TCMalloc管理。栈对象则由修改版LLVM SafeStack分析和组织：需要保护的对象被放入按尺寸类别划分的unsafe stack区域，并使用对应标签。

### 2.2 确定性16标签轮转

同一尺寸类别区域中的对象槽使用确定性的16标签周期。可将其抽象为：

```text
槽位：  1  2  3  4  ...  15  16  17  18
标签：  0  1  2  3  ...  14  15   0   1
```

对于任意一个对象槽，距离它1至15个槽位的对象具有不同标签。因此，从当前对象跨入这些槽位时，原指针标签与目标内存标签不匹配，MTE会产生故障。第16个槽位重新使用相同标签，因此保护范围是有限的。在相同尺寸类别中，单方向可表达的保证范围为：

```text
15 × size_class 字节
```

例如，16字节尺寸类别对应240字节的单方向保护距离；尺寸类别越大，标签周期形成的字节保护范围也越大。

### 2.3 标签持久性

StickyTags中的“sticky”表示标签与槽位空间位置保持稳定关系。对象被释放后，相同地址再次用于同一尺寸类别对象时，内存标签不需要重新随机选择。持久标签具有两个作用：

1. 维持确定性的空间布局，使附近对象的标签关系不受分配历史影响；
2. 减少每次分配、释放时重新标记内存产生的开销。

标签持久性不能解释为use-after-free保护。相反，旧指针可能继续匹配被复用槽位的标签。论文默认StickyTags把全部标签资源用于空间保护，并没有把时间错误作为核心保护目标。

### 2.4 堆保护

修改版TCMalloc利用已有的尺寸类别组织堆对象，并使相邻槽位遵循确定性标签轮转。堆分配返回的指针携带逻辑标签；对象所在内存带有分配标签。当带标签指针越界进入标签不同的附近槽位时，MTE检测到不匹配并产生故障。

### 2.5 栈保护

修改版LLVM SafeStack负责栈对象保护。编译器分析需要放入unsafe stack的对象，为不同尺寸类别建立栈区域，并在生成代码时为指针应用标签。由于栈帧会被重复进入和退出，持久标签可以避免递归或重复函数调用过程中频繁重新标记相同栈区域。

### 2.6 相较传统方法的优势与限制

| 对比项 | 传统随机标签 | StickyTags |
|---|---|---|
| 标签生成 | 分配时随机选择 | 根据对象槽位置确定 |
| 保护性质 | 概率性 | 标签周期范围内确定性 |
| 相邻对象标签 | 可能随机相同 | 前15个相邻槽位不同 |
| 标签是否依赖保密 | 通常依赖攻击者难以猜中 | 不依赖标签保密 |
| 内存重新标记 | 分配和释放时可能重复进行 | 首次初始化后保持持久 |
| 主要目标 | 概率检测空间或时间错误 | 有界空间错误保护 |

StickyTags仍然存在边界：第16个槽位开始标签重复；MTE的16字节粒度可能无法检测落入对象填充区的小越界；未标记的兼容代码和特殊栈操作可能带来兼容性问题；默认设计不提供确定性的时间安全。

### 5.2 启用MTE故障模式

测试程序首先允许进程使用带标签地址，并启用异步MTE故障。代码同时启用全部16个标签值：

```c
static void configure_mte_fault_mode(void) {
    unsigned long control = PR_TAGGED_ADDR_ENABLE | PR_MTE_TCF_ASYNC |
                            (0xffffUL << PR_MTE_TAG_SHIFT);
    if (prctl(PR_SET_TAGGED_ADDR_CTRL, control, 0, 0, 0) != 0) {
        perror("prctl(PR_SET_TAGGED_ADDR_CTRL)");
        exit(2);
    }
}
```

如果`prctl`失败，程序以状态2退出，防止在MTE没有正确启用时继续执行并产生错误结论。

### 5.3 提取指针标签和原始地址

测试需要分别获得指针的逻辑标签和去掉高字节标签后的地址：

```c
#define ADDRESS_MASK 0x00ffffffffffffffULL

static unsigned pointer_tag(const void *pointer) {
    return (unsigned)(((uintptr_t)pointer >> 56) & 0x0f);
}

static uintptr_t raw_address(const void *pointer) {
    return ((uintptr_t)pointer) & ADDRESS_MASK;
}
```

`pointer_tag`用于检查标签周期，`raw_address`用于比较对象实际地址、排序对象和确认相邻关系。

### 5.4 区分MTE故障和普通段错误

仅观察程序以139退出并不能证明StickyTags检测成功，因为普通非法地址也可能导致`SIGSEGV`。测试程序读取`siginfo_t.si_code`并输出故障类型：

```c
const char *kind = "other SIGSEGV";
if (info->si_code == SEGV_MTEAERR) {
    kind = "SEGV_MTEAERR (asynchronous MTE tag check fault)";
}
if (info->si_code == SEGV_MTESERR) {
    kind = "SEGV_MTESERR (synchronous MTE tag check fault)";
}
```

异步模式下预期获得`SEGV_MTEAERR`和`si_code=8`。普通段错误会被单独标记为`unexpected_sigsegv`，不能计入MTE故障数。

### 5.5 堆越界功能测试

堆测试分配两个32字节对象。正常模式只访问`first[0]`和`first[31]`；越界模式写入`first[32]`：

```c
volatile unsigned char *first = malloc(32);
volatile unsigned char *second = malloc(32);

first[0] = 0x11;
first[31] = 0x22;

if (overflow) {
    first[32] = 0x33;
}
```

protected程序中的两个对象由修改版TCMalloc管理。`first[32]`跨入相邻对象槽后，源指针标签与目标槽标签不同，预期产生MTE故障。baseline执行同一源码但没有StickyTags标签布局，预期不会产生MTE标签故障。

### 5.6 栈越界功能测试

栈对象的实际地址顺序可能受编译器布局影响，不能直接假定第二个数组位于第一个数组之后。测试先去掉标签并比较地址，确认两个32字节数组严格相邻，再从低地址对象向高地址对象越界：

```c
uintptr_t first_raw = raw_address((const void *)first);
uintptr_t second_raw = raw_address((const void *)second);
volatile unsigned char *lower = first_raw < second_raw ? first : second;
uintptr_t lower_raw = first_raw < second_raw ? first_raw : second_raw;
uintptr_t upper_raw = first_raw < second_raw ? second_raw : first_raw;

if (upper_raw - lower_raw != sizeof(first)) {
    return 3;
}
lower[index] = 0x55;
```

当`index=31`时访问仍在对象内部；当`index=32`时访问进入相邻对象。布局不满足严格相邻条件时，程序返回3，不把不确定访问当作有效越界证据。

### 5.7 标签轮转测试

机制程序分配并按原始地址排序32个对象，检查三个条件：前16个标签是否互不相同、相邻对象标签是否不同、相隔16槽的对象标签是否重复：

```c
int pass = count >= 32 && unique_first16 == 16 &&
           adjacent_diff == count - 1 && repeat16 == 16 && exact_stride;
```

其中`exact_stride`确认对象之间的地址差等于尺寸类别，避免在非连续布局上错误推断标签周期。

### 5.8 边界距离测试

边界测试选择一段连续对象，把起始对象的带标签指针重新组合到第`slot`个目标槽原始地址，然后执行访问：

```c
volatile unsigned char *attack =
    retagged_pointer((const void *)objects[start].ptr,
                     objects[start + slot].raw);
int expected_fault = objects[start].tag != objects[start + slot].tag;
attack[0] = 0x5a;
```

当目标槽标签不同，预期产生MTE故障；第16槽标签与起始槽重复，预期访问不产生标签故障。该测试直接验证有限距离空间保护边界。

### 5.9 标签持久性测试

持久性测试记录原始地址与第一次观察到的标签。相同地址再次出现时比较标签：

```c
if (state->raw[i] == raw) {
    ++state->reuses;
    if (state->tag[i] != tag) {
        ++state->mismatches;
    }
    return;
}
```

测试只有在地址确实发生复用、标签不一致次数为0且地址跟踪表没有溢出时才通过。这避免了“没有地址复用所以没有标签变化”的无效结论。

### 5.10 MTE粒度测试

粒度测试使用逻辑大小为10字节、实际槽大小为16字节的对象，分别访问下标9、10、15、16和32。测试根据`index / 16`计算目标槽：

```c
int target_slot = index / 16;
uintptr_t target_raw = objects[start].raw + (uintptr_t)index;
```

下标10和15虽然超过逻辑对象长度，但仍位于同一个16字节MTE粒度内，预期不产生标签故障；下标16和32进入其他槽，预期发生故障。该实验验证的是MTE底层粒度限制，不能单独表述为StickyTags创新。

### 5.11 自动运行和断言

Shell运行器设置单用例超时，提取退出状态、故障类型和`si_code`，然后根据版本及用例设置预期：

```bash
if [[ $variant == protected && $case_name != normal ]]; then
    expected_fault=1
    expected_status=139
else
    expected_fault=0
    expected_status=0
fi

if [[ $status -eq $expected_status && $fault -eq $expected_fault &&
      $unexpected_sigsegv -eq 0 ]]; then
    pass=1
else
    pass=0
fi
```

因此，protected没有产生预期MTE故障、baseline意外产生MTE故障、正常访问异常退出、出现普通段错误或用例超时都会使测试失败。

## 8. 结果分析与讨论

### 8.1 与论文核心主张的对应关系

| 论文核心设计 | 本实验验证方式 | 观察结果 | 支持情况 |
|---|---|---|---|
| 按尺寸类别组织对象 | 连续布局与步长检查 | 堆、栈cycle用例均满足`stride_ok=1` | 支持 |
| 确定性16标签轮转 | 32对象标签检查 | 前16个标签唯一，相隔16槽重复 | 支持 |
| 有限距离空间保护 | 第1至16槽边界测试 | 第1至15槽故障，第16槽不故障 | 支持 |
| 持久标签 | 地址复用标签比较 | 9990次复用中标签变化为0 | 支持 |
| 堆和栈均受保护 | 堆、栈越界与机制矩阵 | 两类protected测试均通过 | 支持 |
| 保护行为来自StickyTags | protected/baseline对照 | protected产生680个预期故障，baseline为0 | 支持 |

这些结果形成了从标签布局、越界行为到基线差异的证据链。仅观察一次段错误不足以支持核心主张，而本实验进一步确认故障类型、重复轮次、标签周期和保护边界。

### 8.2 StickyTags优势的实验体现

与随机标签相比，StickyTags最直接的优势体现在边界测试中。第1至15个目标槽位在全部尺寸、堆栈类型和重复轮次中均产生预期标签不匹配，没有出现随机碰撞。第16槽稳定不产生故障，则说明实验同时观察到了方法的理论边界，而不是把所有崩溃都归因于保护成功。

持久性结果显示，同一地址被复用时标签保持不变。结合标签轮转结果，可以确认标签不是全部为0，也不是每次分配重新随机选择，而是与空间槽位稳定关联。这与StickyTags通过持久标签减少反复标记的设计一致。不过，本实验没有测量运行时间，因此不能用该结果直接量化性能优势。

### 8.3 功能对照的意义

protected和baseline由相同C源码生成，可以减少测试逻辑差异。二者的主要区别是protected启用修改版SafeStack并链接修改版TCMalloc，而baseline不启用这些组件。相同越界在baseline中0/20产生MTE故障，在protected中20/20产生MTE故障，说明故障行为与StickyTags配置相关，而不是测试程序天然会崩溃。

baseline不能替代论文中的全部对比系统。论文还与MemTagSanitizer、Scudo及其他方案比较，而本实验只设置了“启用StickyTags”和“未启用StickyTags”两种配置。因此，本实验能够支持基本因果对照，不能支持论文级方案优劣和性能比较。

### 8.4 检测与缓解的区别

粒度测试中的下标10和15已经超过10字节逻辑对象，但没有触发MTE故障，因为访问仍在同一个16字节分配粒度内。这说明“没有故障”不一定意味着访问仍符合C语言对象边界，也不应把MTE描述为字节级完整边界检查。

另一方面，只要访问尚未跨入其他对象槽，它可能仍无法破坏相邻对象。论文区分检测与缓解：某些落入填充区的访问不会被立即检测，但空间布局仍可能阻止它到达其他对象。本实验只验证了故障行为和粒度，没有对所有此类访问的可利用性进行分析。

### 8.5 实验可信度

为提高结果可信度，本实验采用以下措施：

1. 固定上游源码提交和工具链版本；
2. 检查protected与baseline二进制依赖，确认配置差异；
3. 对堆、栈和多种尺寸分别测试；
4. 对边界和粒度用例进行重复运行；
5. 同时检查退出状态、MTE专用故障类型和普通段错误；
6. 将布局不可用记录标记为`SKIP`而不是成功；
7. 对持久性测试检查地址确实复用并检测跟踪表溢出；
8. 保存原始日志和结果摘要。

860条机制测试全部通过，且预期与实际MTE故障数完全一致。完整对照没有`comparison_status=fail`记录。上述结果说明当前合成实验具有较好的一致性，但不能消除模拟环境和测试数据范围带来的外部有效性限制。

### 8.6 当前复现限制

本实验的主要限制如下：

1. **QEMU模拟环境。** QEMU可以模拟MTE标签行为，但其运行时间不能代表真实硬件；
2. **合成测试。** 测试程序针对论文机制设计，尚未覆盖大型真实应用的复杂内存布局；
3. **没有SPEC性能数据。** 无法验证论文报告的运行时间和内存开销；
4. **没有Juliet和真实CVE。** 无法给出标准漏洞集检测率或真实漏洞缓解率；
5. **没有真实设备侧信道实验。** 未复现论文对随机标签泄漏的攻击证据；
6. **baseline较简单。** 只比较未保护程序，没有复现论文中的其他先进方案；
7. **不是完整空间安全。** 第16槽标签重复，MTE还存在16字节粒度限制；
8. **不验证时间安全。** 标签持久性不能作为use-after-free保护证据。

因此，本实验结果适合支持“StickyTags核心标签分配和有限距离空间保护机制已经在QEMU AArch64 MTE环境中完成初步复现”，不适合支持“论文全部实验已复现”或“已验证真实硬件性能”等更强结论。
