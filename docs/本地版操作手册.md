# 本地版操作手册

本文只说明如何使用当前电脑上已经准备好的 StickyTags 本地复现环境，不涉及版本管理或远程仓库操作。操作重点是启动本地 QEMU MTE 虚拟机、编译测试程序、运行测试、判断结果和关闭环境。

当前电脑使用以下目录：

| 内容 | 本地位置 |
|---|---|
| Windows项目目录 | `F:\Paper\StickyTags\ST` |
| WSL中的项目目录 | `/mnt/f/Paper/StickyTags/ST` |
| WSL发行版 | `StickyTagsLab` |

| QEMU客体测试目录 | `/opt/stickytags` |

本地环境结构为：

```text
Windows项目文件
  -> WSL2构建和控制环境
  -> QEMU AArch64 Linux客体
  -> Arm MTE功能测试
```

WSL本身是`x86_64`构建主机，真正执行StickyTags测试的是QEMU中的`aarch64`客体。

## 2. 本地代码分别负责什么

### 2.1 论文作者实现

本地目录 `/home/brave/stickytags-lab/src/stickytags` 保存论文作者提供的实现，固定版本为：

```text
db3ba2616ce0935fba6352192a43010ba9d3172a
```

当前复现使用其中的：

- 修改版LLVM/SafeStack：负责栈对象尺寸分类、指针标签和标签布局；
- 修改版gperftools/TCMalloc：负责堆对象尺寸分类和标签布局；
- `test/test.c`：打印作者示例中的堆、栈地址和标签，只作为布局探针。

`test/test.c`本身不执行越界访问，因此不能单独证明StickyTags保护成功。

### 2.2 本地复现项目代码

Windows项目目录中的代码负责验证论文实现：

- `Experiment/tests/stickytags-functional.c`：正常访问、堆越界和栈越界；
- `Experiment/tests/stickytags-mechanism.c`：标签轮转、边界距离、标签持久性和MTE粒度；
- `Experiment/build-*.sh`：把测试程序交叉编译为AArch64程序；
- `Experiment/run-*.sh`：在QEMU客体中运行并自动判断结果；
- `Experiment/start-mte-vm.sh`、`wait-for-mte-vm.sh`、`stop-mte-vm.sh`：控制本地虚拟机。

所以，本地复现不是重新编写StickyTags核心算法，而是运行论文作者实现，并用自行设计的测试验证其核心行为。

## 3. 如何判断命令成功

在WSL中，命令结束后可以立即执行：

```bash
echo $?
```

- 输出`0`：外层命令成功；
- 输出非`0`：命令失败，不能继续把结果视为有效实验结果。

本文使用：

```bash
某个命令 && echo "XXX_SUCCESS"
```

只有前面的命令返回0，才会显示成功标志。

需要区分两种退出状态：

- 被测试的越界子程序返回139，并且故障类型是`SEGV_MTEAERR`或`SEGV_MTESERR`，可以是预期成功结果；
- 负责判断测试的外层`run-*.sh`脚本最终必须返回0。

状态137通常表示超时终止，不算MTE保护成功。

## 4. 演示前本地检查

### 4.1 进入本地WSL环境

在Windows PowerShell中运行：

```powershell
wsl -d StickyTagsLab
```

进入WSL后运行：

```bash
uname -m
cd /mnt/f/Paper/StickyTags/ST
pwd
```

**成功标准：**

- `uname -m`输出`x86_64`；
- `pwd`输出`/mnt/f/Paper/StickyTags/ST`；
- 命令没有出现“目录不存在”或权限错误。

### 4.2 载入本地配置

```bash
source Experiment/lab-env.sh && echo "LOCAL_CONFIG_READY"
printf 'LAB_ROOT=%s\nVM=%s:%s\nUSER=%s\n' \
    "$STICKYTAGS_LAB_ROOT" "$STICKYTAGS_VM_HOST" \
    "$STICKYTAGS_VM_PORT" "$STICKYTAGS_VM_USER"
```

**成功标准：** 显示`LOCAL_CONFIG_READY`，默认实验目录为`/home/brave/stickytags-lab`，虚拟机地址为`127.0.0.1:2222`，用户为`brave`。

### 4.3 检查本地虚拟机文件

```bash
test -f "$STICKYTAGS_LAB_ROOT/vm/boot/Image-6.8.0-137-generic" &&
test -f "$STICKYTAGS_LAB_ROOT/vm/boot/initrd.img-6.8.0-137-generic" &&
test -f "$STICKYTAGS_LAB_ROOT/vm/images/stickytags-arm64-overlay.qcow2" &&
test -f "$STICKYTAGS_LAB_ROOT/vm/cloud-init/seed.img" &&
test -f "$STICKYTAGS_SSH_KEY" &&
echo "LOCAL_VM_ASSETS_READY"
```

**成功标准：** 显示`LOCAL_VM_ASSETS_READY`。

**失败含义：** 没有显示成功标志，说明本地内核、initrd、磁盘镜像、cloud-init镜像或SSH密钥至少缺少一个。

### 4.4 检查本地工具链

```bash
test -x "$STICKYTAGS_LAB_ROOT/build/llvm-rel-gcc13/bin/clang" &&
test -f "$STICKYTAGS_LAB_ROOT/build/llvm-rel-gcc13/lib/clang/16/lib/linux/libclang_rt.safestack-aarch64.a" &&
test -f "$STICKYTAGS_LAB_ROOT/build/gperftools-aarch64-install/lib/libtcmalloc.so.4.5.10" &&
echo "LOCAL_TOOLCHAIN_READY"
```

**成功标准：** 显示`LOCAL_TOOLCHAIN_READY`。

**失败含义：** 修改版Clang、AArch64 SafeStack运行库或StickyTags TCMalloc尚未准备完整，需要执行第5节的本地构建。

## 5. 本地工具链缺失时如何重新构建

当前电脑已经存在工具链，正常演示可以跳过本节。只有第4.4节检查失败时才需要执行：

```bash
./Experiment/configure-llvm.sh && echo "LLVM_CONFIGURED"
./Experiment/build-llvm.sh && echo "LLVM_BUILT"
./Experiment/configure-compiler-rt-aarch64.sh && echo "COMPILER_RT_CONFIGURED"

ninja -C "$STICKYTAGS_LAB_ROOT/build/compiler-rt-aarch64" \
    clang_rt.safestack-aarch64 && echo "SAFESTACK_RUNTIME_BUILT"

resource_dir=$("$STICKYTAGS_LAB_ROOT/build/llvm-rel-gcc13/bin/clang" \
    --print-resource-dir)
install -Dm644 \
    "$STICKYTAGS_LAB_ROOT/build/compiler-rt-aarch64/lib/linux/libclang_rt.safestack-aarch64.a" \
    "$resource_dir/lib/linux/libclang_rt.safestack-aarch64.a" &&
echo "SAFESTACK_RUNTIME_INSTALLED"

./Experiment/build-gperftools-aarch64.sh && echo "TCMALLOC_BUILT"
./Experiment/validate-gperftools-aarch64.sh && echo "TCMALLOC_VALIDATED"
```

**完整成功标准：** 依次显示：

```text
LLVM_CONFIGURED
LLVM_BUILT
COMPILER_RT_CONFIGURED
SAFESTACK_RUNTIME_BUILT
SAFESTACK_RUNTIME_INSTALLED
TCMALLOC_BUILT
TCMALLOC_VALIDATED
```

已经构建过的Ninja目标可能显示`ninja: no work to do`，这也属于成功。出现`ninja: build stopped`、链接错误或任一成功标志缺失，都说明本地构建没有完成。

## 6. 推荐的本地演示顺序

### 第一步：启动本地MTE虚拟机

```bash
./Experiment/start-mte-vm.sh && echo "LOCAL_VM_PROCESS_STARTED"
./Experiment/wait-for-mte-vm.sh && echo "LOCAL_VM_SSH_READY"
```

**成功标准：**

- 启动脚本输出QEMU PID和控制台日志路径，或者提示QEMU已经运行；
- 等待脚本输出`SSH_READY`；
- 最后显示`LOCAL_VM_PROCESS_STARTED`和`LOCAL_VM_SSH_READY`。

**失败含义：** 输出`SSH did not become ready`、QEMU启动错误，或缺少`LOCAL_VM_SSH_READY`。QEMU TCG启动可能需要数分钟，不要在等待期间重复启动。

### 第二步：编译本地测试程序

```bash
./Experiment/build-functional-tests-aarch64.sh && echo "FUNCTIONAL_BINARIES_BUILT"
./Experiment/build-baseline-aarch64.sh && echo "BASELINE_BINARY_BUILT"
./Experiment/build-mechanism-tests-aarch64.sh && echo "MECHANISM_BINARIES_BUILT"
```

**成功标准：**

- 三个成功标志全部出现；
- 输出显示目标程序是AArch64 ELF；
- protected程序包含`__safestack_init`并依赖`libtcmalloc`；
- baseline程序的SafeStack符号数和TCMalloc依赖数都是0。

**失败含义：** 出现编译或链接错误、找不到SafeStack运行库、找不到TCMalloc，或任一成功标志缺失。

### 第三步：部署到本地QEMU客体

```bash
./Experiment/deploy-functional-tests.sh && echo "LOCAL_TESTS_DEPLOYED"
```

**成功标准：**

- 输出列出`/opt/stickytags/bin`下的四个测试二进制；
- 输出列出`/opt/stickytags/lib/libtcmalloc.so`；
- `ldd`没有显示`not found`；
- 最后显示`LOCAL_TESTS_DEPLOYED`。

### 第四步：运行四个基础功能测试

```bash
./Experiment/run-functional-tests-in-vm.sh && echo "LOCAL_FUNCTIONAL_TESTS_SUCCESS"
```

四个用例的成功结果是：

| 用例 | 成功结果 |
|---|---|
| `normal` | `EXIT_STATUS=0`、`MTE_FAULT=0`、`PASS=1` |
| `upstream-layout-probe` | 输出非零标签、`EXIT_STATUS=1`、`MTE_FAULT=0`、`PASS=1` |
| `heap-oob` | `EXIT_STATUS=139`、`MTE_FAULT=1`、MTE专用故障、`PASS=1` |
| `stack-oob` | `EXIT_STATUS=139`、`MTE_FAULT=1`、MTE专用故障、`PASS=1` |

运行后检查：

```bash
awk '
    /^PASS=1$/ { passed++ }
    /^PASS=0$/ { failed++ }
    END { printf "passed=%d failed=%d\n", passed + 0, failed + 0 }
' "$STICKYTAGS_LAB_ROOT/logs/stage6-functional-test-results.txt"
```

**成功标准：** 显示`LOCAL_FUNCTIONAL_TESTS_SUCCESS`，统计输出`passed=4 failed=0`。堆、栈越界还必须出现`kind=SEGV_MTEAERR`或`kind=SEGV_MTESERR`，普通段错误不能算成功。

### 第五步：运行本地保护版/未保护版快速对照

课堂演示建议每种越界重复5次：

```bash
./Experiment/run-comparison-in-vm.sh 5 && echo "LOCAL_QUICK_COMPARISON_SUCCESS"
```

**成功标准：**

```text
baseline正常访问：0次MTE故障
protected正常访问：0次MTE故障
baseline堆越界：0% MTE故障
baseline栈越界：0% MTE故障
protected堆越界：100% MTE故障
protected栈越界：100% MTE故障
```

同时必须显示`LOCAL_QUICK_COMPARISON_SUCCESS`。检查CSV：

```bash

    "$STICKYTAGS_LAB_ROOT/logs/stage7-comparison-results.csv"
```

输出`0`表示所有记录都符合对应版本的预期。5轮共产生22条数据记录；20轮共产生82条数据记录。

### 第六步：展示本地已有完整结果

```bash

cat results/summary/protected-baseline-summary.txt
```

`cat`成功只表示文件能够读取。实验结果成功还必须满足：

**成功标准：** 输出`QEMU_STOPPED`或`QEMU_ALREADY_STOPPED`，最后显示`LOCAL_VM_SHUTDOWN_SUCCESS`。

**失败含义：** 输出`QEMU_STILL_RUNNING`或没有出现成功标志。

## 10. 本地常见问题

### 10.1 SSH未就绪

```bash
tail -n 80 "$STICKYTAGS_LAB_ROOT/logs/qemu-mte-console.log"
```

成功执行该命令只表示控制台日志可以读取。需要继续等待`wait-for-mte-vm.sh`输出`SSH_READY`，才能运行测试。

### 10.2 用例状态137

137表示用例被超时强制终止，不是MTE故障。增加本地超时后重新运行：

```bash
export STICKYTAGS_CASE_TIMEOUT=180
echo "$STICKYTAGS_CASE_TIMEOUT"
```

输出`180`表示当前shell的新超时配置已经生效。

### 10.3 普通段错误

以下输出不能单独算作测试成功：

```text
Segmentation fault
EXIT_STATUS=139
```

必须同时确认故障类型为：

```text
kind=SEGV_MTEAERR
```

或：

```text
kind=SEGV_MTESERR
```

### 10.4 演示过程中断

如果完整测试中断，不要把不完整日志当作新结果。先关闭虚拟机，保留项目中已有的完整归档摘要；需要重新验证时只运行失败用例或课堂快速测试，不必每次重新运行1720条。
